Declarative agent + skills

The agent is a YAML file. What it knows how to do is a set of SKILL.md folders it loads on demand. What it must never do is code the model cannot argue with. Built on Google ADK 2.9.2 and driven end to end by the tests in this folder.
1 · Declare

root_agent.yaml

name: governed_project_agent
model: gemini-2.5-flash
instruction: |  # load a skill first ...
tools:
  - name: declarative_agent.skill_set.skill_toolset
before_model_callbacks:
  - name: ...callbacks.llm_call_budget
before_tool_callbacks:
  - name: ...callbacks.tool_guardrail

Change the prompt, model or wiring by editing text. No Python class to rebuild.

2 · Load

ADK builds the agent

from_config(root_agent.yaml) returns a normal LlmAgent and resolves each dotted path to real Python: the skill toolset and the two callbacks. ADK's own server (adk api_server) can serve the same folder.

YAML cannot pass constructor arguments, so anything configured (the skills list, the extra tools) is built in Python once and referenced by name.

3 · Skills

Knowledge on demand

L1name + description is always visible (list_skills): when to use it.
L2The SKILL.md body loads only when the model calls load_skill.
L3references/ files load only when asked (load_skill_resource).
skills/ governed-sql/ → unlocks run_governed_sql write-back-approval/ → unlocks stage_write_back evidence-and-citations/ loop-and-budget-discipline/
4 · Guardrails

Code, not prompts

before_model_callback: a hard cap on model calls per question (45, the requirement value). At the cap it stops and returns a partial answer built only from evidence already gathered.

before_tool_callback: parses the SQL into an AST and blocks DDL/DML, SELECT *, unbounded scans, other users' tables and masked columns. Unparseable means blocked.

One real turn (replayed by the tests with a scripted model)

"How late is piling at Chennai DC-1?" Watch the tool list the model can see: run_governed_sql does not exist for it until the governed-sql skill is loaded.

Why declarative

  • The prompt, model and wiring are reviewable text, so changes are small diffs.
  • A domain expert can edit a skill without touching Python.
  • The same agent loads in ADK web, the API server and tests unchanged.

Why skills

  • The prompt stays short: detail loads only when needed.
  • A skill can gate tools: no skill, no tool, so risky capabilities are opt-in per task.
  • Each skill is a folder with an owner, a description and a test.

What it does not give you

  • The guard is defence in depth: the database must still enforce row filters and masks.
  • A weak model can still ignore a skill's advice; only the callbacks are guaranteed.
  • ADK marks config-based agents as experimental in this version.
Honest notes. Everything shown ran with a scripted stand-in model, not Gemini or Claude, because no API key was available while building; run it once with a real key before relying on the model's behaviour. The tables in the demo are synthetic. The rules come from requirement scenarios ADK-02, ADK-07, GOV-01, GOV-02, GOV-05, BKD-01 and BKD-04 in the supplied Project SLM list.
